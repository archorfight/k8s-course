第 9 章 资源管理 — requests/limits/QoS/驱逐（坑 1-3） ​

心智图：

调度看 requests, 运行看 limits, 驱逐看 QoS: ​

​

requests: 调度器拿它算"这个节点放不放得下" → 决定Pod去哪个Node (只影响调度) ​

limits: 运行时的硬顶 → CPU=限流(饿不死,但慢), 内存=OOMKill(超了直接杀) ​

QoS等级(自动推导): ​

Guaranteed = 每个容器 requests==limits(CPU&内存都设) → 最后被驱逐 ​

Burstable = 设了requests, limits>requests → 中间 ​

BestEffort = 啥都没设 → 第一个被驱逐+无限抢占 ​

节点内存吃紧 → kubelet按QoS+超request幅度排序驱逐(OOM score) ​

``` ​

这是"资深开发者 10 个坑"的第一簇。坑 1：裸 Pod 不设资源；坑 2：CPU limit 导致长尾延迟；坑 3：内存 limit 与 JVM/运行时不匹配。

开篇判断 ​

  1. requests 和 limits 分别被谁消费？2) 我的服务 P99 毛刺但"什么都没错"，我查过 CPU throttle 吗？3) QoS 三级我的服务是哪级、被驱逐时排在第几？本章三个坑（含本课程 37 倍实测数据）都是"看起来没问题"的问题。

9.1 两个数字的分工：requests 给调度器，limits 给内核 ​

yaml
resources:
  requests: { cpu: 500m, memory: 1Gi }   # 500m = 0.5核
  limits:   { cpu: "2",  memory: 2Gi }
  • CPU limit 的实现是 CFS throttling：每个 100ms 周期给容器 limit/核数×100ms 的配额，用完就冻结到下个周期。后果：CPU limit=500m 的容器哪怕节点空闲，任何 50ms 级的计算任务也会被切成两半、多付一个周期的延迟。对延迟敏感服务（在线 API、GC！），CPU limit 是长尾延迟的头号嫌疑——JVM 的 GC 线程 burst 被 throttle，一次 Young GC 变成 30ms 的停顿变成 200ms。
  • 内存 limit 没有 throttle，只有 OOMKill：超过 → cgroup OOM → SIGKILL(137)，进程连日志都来不及写。所以内存 limit 的哲学是"宁可设宽"，CPU limit 的哲学是"要么不设，要么设得足够 burst"。

9.2 坑 1：不设 requests 的连锁灾难 ​

裸 Pod（什么资源都不写）= BestEffort。三条灾难链：

  1. 调度器对它"零成本"——全塞到一个节点，节点过载，然后它又是第一个被驱逐的（QoS 最低）。Pod 在节点间反复横跳，就是典型的 BestEffort 漂流。
  2. 节点内存压力下，kubelet 驱逐顺序：BestEffort（不管用没用超）→ 超 requests 最多的 Burstable → Guaranteed。裸 Pod = 随时献祭。
  3. HPA 基于 CPU utilization = usage/requests。没 requests 的 Pod，HPA 直接拿不到指标（分母不存在），伸缩失效。

9.3 坑 2：CPU limit 的长尾延迟陷阱（附实测方法） ​

Google/SUSE 都有公开数据：盲目设 CPU limit 会显著抬升 P99。业界主流实践分两派：

  • 派 A（Google Borg 传统）：只设 CPU requests，不设 CPU limit（内存仍设 limit）。让 burst 吃节点空闲。风险：恶意/失控容器可饿死邻居——由 namespace 级 ResourceQuota/LimitRange 兜底。
  • 派 B（成本强约束）：limit=request（Guaranteed），用扩副本数换确定性。

给 Java 服务的具体建议（10 年 Java 的你可直接抄）：requests.cpu=日常均值的 1.5 倍；CPU limit 不设或 ≥ requests 的 4 倍；内存 requests=limits=容器稳定态 RSS × 1.2。实测方法（第 12 章会用 metrics-server）：

bash
kubectl top pod -l app=web --containers    # 看真实usage vs requests
# 观察throttle(节点上): cat /sys/fs/cgroup/cpu/cpu.stat 或容器内 /sys/fs/cgroup/cpu.stat 的 nr_throttled

9.4 坑 3：JVM/Python 的内存 limit 错配 ​

OOMKilled 的排查公式：limits.memory 必须覆盖"堆 + 堆外"。堆外包括：metaspace、code cache、线程栈（每线程 ~1MB×200线程=200MB）、直接内存（Netty!）、glibc malloc 碎片。

  • JVM：-XX:MaxRAMPercentage=70（预留 30% 堆外），并显式限 -XX:MaxDirectMemorySize。
  • Python/Node：解释器本身 RSS 底噪 ~30-80MB，vLLM/PyTorch 还有 CUDA 上下文（第 13 章，GPU 显存是另一本账，和 limits.memory 无关）。
  • 观测工具：Pod 已挂的情况下用 kubectl describe 的 last state 看 OOMKilled；事前用本地 docker run -m 2g --memory-swap 2g 复现 RSS 峰值。⚠️ 内存泄漏的形态是 RSS 缓慢爬坡到 limit 周期性 137——kubectl top pod 按小时采样画曲线最直观。

9.5 集群级护栏：ResourceQuota 与 LimitRange ​

namespace 是多团队的租户边界，配两个护栏：

yaml
apiVersion: v1
kind: ResourceQuota          # 团队namespace总闸
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.memory: 60Gi
    pods: "100"
---
apiVersion: v1
kind: LimitRange             # 单Pod下限保护: 强制默认requests/limits
spec:
  limits:
  - type: Container
    defaultRequest: { cpu: 100m, memory: 128Mi }
    default:        { cpu: "1",  memory: 1Gi }

LimitRange 的妙处：忘写资源的 Pod 会被自动注入默认值（不再 BestEffort），而不是被拒绝——护栏与开发者体验兼得。ResourceQuota 则在超闸时直接拒绝创建（apply 报 exceeded quota），这是"为什么我的 Deployment 起不来"的一个经典答案。

9.6 requests 该填多少：一个可复制的流程 ​

  1. 压测或灰度期 kubectl top pod --containers 每 5 分钟采样，取 P95。
  2. requests = P95 × 1.2~1.5；内存 requests=limits=P95 峰值 × 1.2。
  3. 上线后每周 review（成本 = Σrequests，request 虚高 = 白烧钱，云上按 request 计费的 reserved capacity 尤甚）。
  4. 用 kubectl describe node 的 Allocated resources 段看节点水位：requests 水位长期 >70% 的节点，滚动发布会卡 Pending（maxSurge 的新 Pod 无处可去——第 4 章预告的坑在这里兑现）。

Lab 9：制造并解剖一次 OOMKilled ​

bash
# 1. 内存limit=50Mi的容器, 让它分配100MB → 必然OOM
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: oom-demo }
spec:
  restartPolicy: Never
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh","-c","dd if=/dev/zero of=/dev/shm/fill bs=1M count=100; sleep 5"]
    resources:
      requests: { memory: 32Mi }
      limits:   { memory: 50Mi }
EOF

# 2. 等待约10秒后看状态
kubectl get pod oom-demo
# NAME       READY   STATUS      RESTARTS
# oom-demo   0/1     OOMKilled   0        ← 认识这个STATUS

kubectl describe pod oom-demo | grep -B2 -A2 "OOMKilled"
# → State: Terminated / Reason: OOMKilled / Exit Code: 137
# (⚠️ 信息在"State"段而非"Last State"——restartPolicy=Never 且没重启过时没有 Last State)

# 3. 体验CPU限流: limit=100m vs 不限流, 各哈希300MB零, 对比耗时
# (⚠️ 原写法 sha256sum /dev/zero | head -c 0 是读无限流, 永不结束也拿不到time输出;
#  另外 busybox ash 里 time 管道尾部的重定向会连 time 报告一起吞掉, 必须套一层 sh -c)
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: throttle-demo }
spec:
  restartPolicy: Never
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh","-c","time sh -c 'dd if=/dev/zero bs=1M count=300 2>/dev/null | sha256sum'"]
    resources:
      limits: { cpu: 100m }
EOF
cat <<'EOF' | kubectl apply -f -        # 对照组: 无limit
apiVersion: v1
kind: Pod
metadata: { name: throttle-base }
spec:
  restartPolicy: Never
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh","-c","time sh -c 'dd if=/dev/zero bs=1M count=300 2>/dev/null | sha256sum'"]
EOF
kubectl wait --for=condition=ready --timeout=60s pod/throttle-demo pod/throttle-base 2>/dev/null; sleep 45
kubectl logs throttle-demo | grep real    # 实测 ~37s
kubectl logs throttle-base | grep real    # 实测 ~1s → CFS throttle不是"慢一点", 是"按配额硬切"

# 4. 清理
kubectl delete pod oom-demo throttle-demo throttle-base

验证点：①OOMKilled + exit 137 的完整证据链会看了；②CPU limit=100m 时 1 秒的计算跑了约 10 秒——throttle 是量化可预测的，这个直觉值 10 次排障。

生产案例：CPU limit 的长尾延迟（本课程实测+公开共识） ​

本课程实测（VERIFICATION.md 第 9 章）：限流 vs 不限流对照组哈希 300MB 耗时 37.4s vs 1.0s（约 36 倍）——CPU throttle 不报错只变慢，是"P99 毛刺查无异常"的头号嫌疑人（throttled_periods 指标才能看见）。另一模式：JVM 在容器里按宿主机内存算堆的世纪坑（UseContainerSupport 之前的年代），OOMKilled 的历史主因。

第 20 章 安全加固 — 从默认不安全到能过审计 ​

20.1 开篇判断 ​

K8s 默认配置的安全姿势是"内部可信"模型，而现实是零信任。三个判断题：

  1. 你的 PodSecurity 标准是哪一个？如果回答不了，你的集群默认允许特权容器——任何能创建 Pod 的用户都能拿节点 root。
  2. 你的 RBAC 有没有人绑 cluster-admin 给"方便调试"？这是渗透测试报告里出现率最高的单点。
  3. 你的 Secret 是 etcd 里裸 base64 吗？（是的，base64 不是加密。）

三个问题任何一个让你皱眉，本章就是给你写的。目标不是变成安全工程师，是让你的集群过一次基本的安全审计。

20.2 原理：五层防线模型 ​

按攻击者路径记（从外到内）：

L1 入口层：API Server 暴露面。公网 0.0.0.0:6443 无认证 = 特斯拉事件剧本（见第 16 章）。底线：API Server 不对公网开、必须开时叠 mTLS+IP 白名单+审计日志。匿名认证（--anonymous-auth）默认值随版本收紧，自查一次。

L2 权限层（RBAC）：核心原则最小权限。高危动词清单：escalate/bind/impersonate——拥有任何一个约等于拥有 cluster-admin（可以给自己授权）。检查命令：kubectl auth can-i --list --as=system:serviceaccount:ns:name，把这条写进 oncall 手册。ServiceAccount 的 automountServiceAccountToken：不需要 API 访问的 Pod 一律 automountServiceAccountToken: false——被 RCE 的 Pod 拿不到集群凭证，爆炸半径从"集群"降到"容器"。

L3 工作负载层（Pod Security Standards）：v1.25 起 PodSecurityPolicy 已删除，接替者是 Pod Security Admission（namespace 级 label：enforce=restricted）。三级基线：privileged（无限制）< baseline（禁最危险项）< restricted（禁特权、强制 runAsNonRoot、seccomp、drop ALL capabilities）。生产默认 posture：系统命名空间 baseline，业务命名空间 restricted，迁移工具 kubectl label --dry-run + verractor/pod-security 审计模式先行。

L4 密钥层：etcd 里 Secret 是 base64 裸奔，能摸 etcd 磁盘/备份的人能读全部密钥。对策三层：etcd 静态加密（EncryptionConfiguration，kubeadm 一行配置，先做这个）；KMS provider 接外部密钥管理（云厂商托管方案）；应用层再上 external-secrets/Sealed Secrets 把密钥从 Git 里摘出来（与第 24 章 GitOps 配套）。

L5 网络层：默认全通。NetworkPolicy 默认拒绝是你要主动建设的（第 22 章专讲）。本章只立一个原则：每个命名空间起步就带一条 deny-all 入站策略，放开是显式行为。

供应链（镜像与依赖）单列一句：admission 强制 imagePullPolicy+签名校验（cosign/Kyverno），防"随便什么镜像都能进集群"。

20.3 实操 lab：给 kind 集群做一次五层加固体检 ​

bash
# ============ L2 权限层 ============
# 1. 找出所有绑了 cluster-admin 的对象（第一条通常就吓人）
kubectl get clusterrolebinding -o json | jq -r '.items[] | select(.roleRef.name=="cluster-admin") | .metadata.name + " <- " + (.subjects|tostring)'
# 逐个审：真的需要吗？删掉：kubectl delete clusterrolebinding <name>

# 2. 模拟一个 SA 能干什么（这条命令请背下来）
kubectl auth can-i --list --as=system:serviceaccount:default:default | head -20

# ============ L3 工作负载层 ============
# 3. 审计模式先行：给业务 ns 打 pod-security 标签（warn 不拦截）
kubectl label ns ai-lab pod-security.kubernetes.io/audit=restricted pod-security.kubernetes.io/warn=restricted --overwrite
# 4. 试着建一个特权 Pod（应被 warn 点名）
kubectl -n ai-lab run evil --image=busybox:1.36 --restart=Never --overrides='{"spec":{"containers":[{"name":"evil","image":"busybox:1.36","command":["sh","-c","sleep 60"],"securityContext":{"privileged":true}}]}}' 
# 观察 warning；然后切成 enforce 再试一次：
kubectl label ns ai-lab pod-security.kubernetes.io/enforce=restricted --overwrite
kubectl -n ai-lab run evil2 --image=busybox:1.36 --restart=Never -- sh -c 'sleep 60'
# 预期：evil2 被 PSA 直接拒绝（错误信息会指出违反哪条 restricted 规则）
kubectl -n ai-lab delete pod evil --ignore-not-found

# ============ L4 密钥层 ============
# 5. 证明 base64 不是加密（一条命令的说服力）
kubectl -n ai-lab create secret generic demo --from-literal=password='P@ssw0rd!'
kubectl -n ai-lab get secret demo -o jsonpath='{.data.password}' | base64 -d; echo
# 输出就是明文。任何能读 secret 的人=持有明文。这就是要上 etcd 加密/KMS 的原因
kubectl -n ai-lab delete secret demo

# 6. 检查 etcd 加密是否开启（kind 默认未开；生产用 kubeadm 的 --encrypt-secret-data 或
#    配置 EncryptionConfiguration 后对存量 secret 做 re-write 才真正落密）
kubectl get secrets -A -o json | jq 'length'   # 存量数，加密改造时要做 rewrite 轮换

# ============ L2 补充：禁自动挂载 ============
# 7. 默认 SA 不自动挂 token
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata: { name: no-token, namespace: ai-lab }
automountServiceAccountToken: false
EOF
# 验证：用它的 Pod 里没有 /var/run/secrets/kubernetes.io/serviceaccount
kubectl -n ai-lab run check --image=busybox:1.36 --restart=Never --serviceaccount=no-token -- ls /var/run/secrets/kubernetes.io/serviceaccount 2>&1 | tail -1
# 预期 No such file or directory
kubectl -n ai-lab delete pod check --ignore-not-found

# ============ 体检汇总 ============
# 8. 有条件的话跑一次官方/社区体检工具（只读）
# kubectl-bench（CIS 基线）或 kube-bench 容器版：
docker run --rm --pid=host aquasec/kube-bench:latest run --benchmark cis-1.11 2>/dev/null | head -40 || echo "kube-bench 未装，跳过（生产集群建议纳入巡检）"

预期总耗时 10-12 分钟。第 4、5 步是给团队做安全培训最好的两段现场演示。

20.4 生产案例：公开复盘与事故模式 ​

案例一（公开事件，可查证）：特斯拉 2018（第 16 章详述过，这里换视角）：无认证 Dashboard → 集群凭证 → 内网横向。防御链路：入口层不暴露（L1）+ automountServiceAccountToken=false（L2）+ NetworkPolicy 限制 Pod 只能访问白名单（L5）。同一事件在三层防线里各自被挡一次——纵深防御的本意。

案例二（公开 CVE，可查证）：CVE-2018-1002105，K8s API server 的 exec/attach 路径升级缺陷，允许任何已认证用户（哪怕只有 namespace 级权限）通过恶意客户端拿到 API server 与 kubelet 通讯的通道，等价于节点权限。修复于 2018 年 12 月。两个行业教训固化下来：①API server 是最高价值目标，版本跟进是安全工程不是例行公事；②这个漏洞的直接后果之一是社区加速了准入与审计日志的默认化。

案例三（行业通病，模式）：CI/CD 凭证泄漏。CI 系统持有集群高权限凭证（为了部署），CI 被注入（开源 PR/依赖投毒）→ 凭证被偷 → 集群沦陷。这是近年 K8s 相关安全事件里占比最高的模式（TeamTNT 等挖矿团伙的公开技战报反复展示该路径）。对策：CI 用短期凭证（TokenRequest/oidc 联邦）而不是长期 ServiceAccount kubeconfig；部署权限收敛到单命名空间+单资源动词。GitOps（第 24 章）在这里同时是效率与安全方案：CI 不再持有集群凭证。

20.5 本章面试题 ​

  1. base64 的 Secret 算加密吗？Secret 的三层保护怎么做？（不算；传输 TLS/etcd EncryptionConfiguration/KMS+应用层 external-secrets）
  2. PodSecurityPolicy 为什么被删？接替者怎么工作？（体验太差/难调试；PSA=namespace label 三模式 audit/warn/enforce + 三级标准）
  3. RBAC 里哪三个动词等价于提权？（escalate/bind/impersonate）
  4. Pod 被 RCE 后攻击者的第一动作是什么？你哪条防线拦它？（找挂载的 SA token；automount=false+最小 RBAC+NetworkPolicy）
  5. etcd 加密改造的坑？（开启只对增量生效，存量 secret 要 rewrite 触发重写，备份里旧密文仍需轮换）

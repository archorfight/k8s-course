第 30 章 求职冲刺 — 面试地图与高频 20 题精写 ​

最后一章是冲刺工具章：先给一张"知识点→章节→考频"的地图，再给 20 道高频题的精写答案。答案按"结论先行→机制→一句话加分项"结构组织，背结构不要背字。

30.1 面试地图（按考频分层） ​

S 级（几乎必考，第 3-11 章）：Pod 生命周期与探针、Deployment 滚动机制、Service 类型与 kube-proxy、requests/limits/QoS、HPA 原理、优雅终止链路、排查 Pending/CrashLoopBackOff。

A 级（资深岗高发，第 9-15、20-27 章）：OOMKilled 与驱逐、Ingress/Gateway API 选型、NetworkPolicy 三定律、RBAC 与 Pod Security、etcd/控制面故障指纹、升级与 API 废弃、GPU 调度（AI 岗 S 级）、成本治理（平台岗 S 级）。

B 级（区分度题）：Operator 原理与幂等、GitOps 四原则、APF/大规模、多集群、服务网格选型、Spot/PDB 耦合。

30.2 高频 20 题精写 ​

1. Pod 的生命周期里，探针分别在什么阶段起作用？readiness 和 liveness 的错误配置会怎样？ ​

启动期：init 容器→主容器启动→startupProbe（若有）先接管，通过前其他探针不跑。运行期：readiness 失败→摘出 Service 端点（不重启）；liveness 失败→重启容器。错误配置经典翻车：liveness 探测一个冷启动慢的依赖（如 JVM 应用），慢≠死，结果 CrashLoop；正确做法慢启动用 startupProbe，就绪用 readiness。加分项：liveness 失败重启会丢本地状态且放大负载（重启风暴），能不配 liveness 就尽量用 readiness。

2. Deployment 的滚动发布是怎么发生的？怎么做到零停机？ ​

本质是两个 RS 的此消彼长：新 RS 按 maxSurge 扩、旧 RS 按 maxUnavailable 缩，每步等新 Pod readiness 通过才继续，progressDeadlineSeconds 超时判 Failed。零停机三件套：readiness 探针准确（新 Pod 就绪才接流）、maxUnavailable=0、配合 Service 端点传播延迟（Pod 就绪≠端点已下发到 kube-proxy，需要 preStop sleep 兜底）。加分项：说出"就绪→端点传播"这几十毫秒到秒级的缝隙是大多数"滚动发布偶发 5xx"的根因。

3. Service 有哪几种？kube-proxy 怎么实现 ClusterIP？ ​

ClusterIP/NodePort/LoadBalancer/ExternalName/Headless。kube-proxy 三种模式：iptables（默认，规则链匹配 DNAT）、IPVS（内核哈希，万级服务时更新与查找都快）、eBPF（Cilium 等内核态直达，无 kube-proxy）。加分项：iptables 模式规则是 O(n) 全量重写，services 上千时一次 endpoint 变更的规则同步要秒到分钟级——这是 IPVS/eBPF 存在的理由。

4. requests 和 limits 的区别？QoS 三级怎么判定？ ​

requests=调度依据（bin-packing 打分）+资源保障；limits=硬上限（CPU 限流，内存超限 OOMKill）。QoS：Guaranteed（每个容器 requests=limits）、Burstable（有 requests 不全等）、BestEffort（都没有）。节点压力驱逐顺序 BestEffort→Burstable（超 requests 越多越先死）→Guaranteed。加分项：CPU 限流是 throttle 不是报错，症状是延迟毛刺，container_cpu_cfs_throttled_periods_total 才能看见；内存 OOMKilled exit code 137。

5. HPA 怎么工作？为什么会抖动？怎么和 VPA 共存？ ​

HPA 控制器周期读指标（metrics API）→期望副本=ceil(当前副本×当前值/目标值)→改 Deployment replicas。抖动来源：指标瞬时尖峰扩容→负载被摊薄→缩容→再尖峰；缓解：目标值留余量、behavior 里的 stabilizationWindowSeconds（缩容冷静期默认 300s）、容忍度 tolerance。VPA 与 HPA 同时改副本会打架，共存方案：VPA 用 Recommendation/Initial 模式（只出建议或只设初始 requests），或用 cluster-proportional 类组件。加分项：HPA 基于 CPU 时，扩容本身会摊薄 CPU 利用率造成缩容诱因——基于 RPS/自定义指标的负反馈更稳。

6. 优雅终止的完整链路？ ​

删 Pod→API 置 terminating（endpoint 同步摘除）→kubelet 发 SIGTERM→容器可捕获处理（排空连接）→preStop hook 先于 SIGTERM 执行→等 terminationGracePeriodSeconds（默认 30s）仍未退出→SIGKILL。坑点：SIGTERM 期间端点可能还没从 kube-proxy 摘干净，preStop sleep 5s 是标准兜底。PDB 保证 voluntary disruption（drain/升级）不突破可用下限，但不防 Pod 崩溃。

7. Pod 一直 Pending，你的排查顺序？ ​

kubectl describe pod 看 Events：集群资源不足（Insufficient cpu/memory→requests 太大或真满了）、GPU 缺 device plugin（节点 GPU 账本空）、亲和性/污点不容忍、PDB/调度约束（topologySpread 无满足点）、quota 超限。加分项：区分"调度不上去"（Pending 无 node）vs"镜像拉不下来"（ImagePullBackOff）vs"起来了不就绪"（Running 但不在 endpoint，readiness 失败）——三类症状三类病。

8. CrashLoopBackOff 一定是因为程序崩吗？ ​

不是。任何容器退出/被杀（OOMKilled、liveness 失败、entrypoint 错误、配置缺失退出）都会进入退避重启循环。排查：kubectl logs --previous（上一次的输出，注意快崩快重启的容器日志可能已被清理，需及时抓或调大退避）、describe 看 Last State（OOMKilled 137 vs Error 1）。加分项：把"日志没来得及看就没了"的坑说出来（sleep 拉长启动或 kubectl logs -f 盯守）。

9. Ingress 和 Gateway API 怎么选？ ​

新集群新入口直接 Gateway API（GA、标准化、分权模型、注解注入面小）；存量 Ingress 大的按域名灰度双轨迁移。核心论据：角色分离（GatewayClass/Gateway 平台组，HTTPRoute 业务组）、status 条件码可排障、ReferenceGrant 跨 ns 默认安全、实现可换。

10. NetworkPolicy 加了默认拒绝后服务全挂，为什么？ ​

egress 策略把 DNS（UDP/TCP 53 到 kube-dns）也挡了，域名解析失败被上层表现为"随机超时"。放行 DNS 是每个 egress 策略的必写项。扩展：三定律（白名单叠加/未选中默认全通/ingress-egress 独立），ipBlock 只用于外部网段。

11. Secret 安全上你做几层？ ​

三层：传输 TLS（默认有）；etcd 静态加密（EncryptionConfiguration，注意存量 rewrite）；密钥不进 Git（External Secrets Operator 从 Vault/KMS 拉）。再加：RBAC 读权限收敛+审计。一句话戳穿：base64 不是加密，任何能 get secret 的主体等于持有明文。

12. RBAC 里最危险的三个动词？ ​

escalate（提角色）、bind（绑角色）、impersonate（冒充）。拥有任一约等于 cluster-admin。审计命令：kubectl auth can-i --list --as=&lt;sa&gt;；同时盘点 cluster-admin 绑定与 automountServiceAccountToken。

13. etcd 对 K8s 意味着什么？你怎么保它健康？ ​

唯一状态存储，raft 多数派写，3 成员容 1 故障。健康三板斧：endpoint status（fsync 延迟、db size）、alarm（NOSPACE 前兆）、定期 snapshot+验证+恢复演练。红线：大对象（几百 KB）×高频 watch 会拖垮全局；控制面全挂时数据面仍在跑（这是设计不是运气）。

14. 集群升级你怕什么？ ​

怕三件事：废弃 API（老 apiVersion 资源在新版消失，pluto 扫描）、CNI/CSI/运行时版本不兼容（节点 NotReady，dockershim 是历史标本）、没有回滚预案（控制面升级可回退幅度有限）。清单：release notes→废弃扫描→兼容矩阵→etcd 备份→演练环境→窗口与回滚线。

15. Operator 是什么？什么时候不该写？ ​

CRD+控制器+领域运维知识，把 runbook 编码成调和循环。reconcile 必须幂等（触发原因不可知）。不该写的三种情况：软件本身简单（Helm/Kustomize 够）、已有成熟 Operator（Postgres 用 CloudNativePG 等）、团队养不起（Operator 自己也是要运维的有状态系统）。评估第三方四条：conditions/conversion/降级/备份。

16. GitOps 和 CI/CD 的区别？selfHeal 为什么重要？ ​

CI 产出镜像与配置提交（push 到 Git），GitOps 控制器从 Git 拉取并调和集群（pull），四原则：声明式/版本化不可变/自动拉取/持续调和。安全增量：CI 不再持集群凭证。selfHeal 关闭时 kubectl 手改会存活，配置漂移、GitOps 名存实亡——"Git 是唯一事实源"要靠它兑现。

17. 大规模集群（千节点级）你会提前做哪些准备？ ​

五件事：CNI/eBPF 数据面（iptables 撑不住万级服务）、NodeLocal DNSCache+CoreDNS 容量、APF 分级与 429 预算、禁裸全量 LIST（informer/分页）、DaemonSet 平台税审计与控制面余量（按目标规模前 30% 配）。发布纪律：错峰+限速。

18. GPU 调度里整卡分配有什么问题？MIG/DRA 解决什么？ ​

小负载独占整卡=账单浪费（行业利用率常年 30-50%）。MIG 硬切隔离（延迟敏感推理）、时间片软共享（吞吐批处理）、DRA 声明式分数粒度+拓扑约束（"4 卡两两 NVLink"）。训练集群必配 gang scheduling（Kueue/Volcano），否则两个 N 卡作业互相卡死。

19. Pod 被 OOMKilled 但容器内存没到 limit，为什么？ ​

两种常见原因：cgroup 层级问题——limit 是 Pod 级（所有容器共享上限，另一个容器吃掉了）；节点内存压力触发的系统级驱逐（eviction，不是 cgroup OOM），看 describe node 的 MemoryPressure 与 kubelet 驱逐记录。加分项：working_set vs rss 的监控口径差异（kubelet 驱逐看 working_set 含 file cache 的口径争议）。

20. 你怎么给自己的 K8s 平台定成本治理路线？ ​

四杠杆按序：可见性（OpenCost 按 ns/标签分摊）→认领（无主负载归零）→右配（P95×1.2-1.5，VPA 建议）→购买策略（基线承诺+弹性 Spot，前提是 PDB+优雅终止扎实）。顺序错了（先买折扣）会把浪费锁死。配套：夜间缩容开发环境、MostAllocated 打包调度。

30.3 面试表达的三条纪律 ​

  1. 结论先行：先一句话答案，再机制，最后加分项；被追问再展开。
  2. 区分事实与模式：讲事故先说来源（"这是公开的 XX 事件/这是我们团队的模式"），不编亲历——第 28 章的案例库就是为此准备的。
  3. 暴露权衡：资深感的来源不是说"X 好"，而是说"X 的代价是 Y，我们在什么条件下接受它"。全书每一章的"选型判断"小节都是这个句式的练习。

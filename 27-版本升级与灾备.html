第 27 章 版本升级与灾备 — 集群的换引擎手术 ​

27.1 开篇判断 ​

  1. 你们集群现在什么版本？上游 n-2 以内吗？（K8s 每年三个次版本，官方只维护最新三个——超出就无安全补丁，这是升级的硬期限。）
  2. 上一次升级是什么时候？有没有"升级前检查清单"这个东西？
  3. 集群彻底丢了（云商说恢复不了）的重建时间，你心里有数吗？RTO 是多少？

升级与灾备是"平时不练、出事要命"的部分。本章给的是可以照抄的工程清单。

27.2 原理 ​

版本生命周期：次版本发布→约 1 年支持期（近版本策略，官方文档为准）。升级的黄金法则：一次一个次版本（1.29→1.30→1.31），跳版本是未定义行为，API 废弃的兼容窗口按此设计。

API 废弃机制（升级事故的最大来源）：API 对象有版本演进（如 policy/v1beta1→policy/v1、batch/v1beta1 CronJob→batch/v1）。废弃的 API 在新版本 API server 直接消失——清单里还写着老 apiVersion 的资源在升级后无法 apply，相关控制器报错。升级前必跑 kubectl-convert/pluto/deprek8 之类的废弃扫描：扫描 GitOps 仓库与集群存量对象里已废弃的 apiVersion。这是升级检查清单的第一条。

升级路径与工具：kubeadm（kubeadm upgrade 三步：升级控制面第一个节点→其余控制面→逐节点 drain+cgroup/kubelet 升级+uncordon）；托管集群（EKS/GKE/AKS）把控制面升级按钮化但节点组升级仍要自己做（drain 策略、PDB 是否允许、DaemonSet 的 maxUnavailable）。节点升级与第 10 章优雅终止/PDB 强耦合：没有 PDB 的集群，节点 drain 就是主动制造停机。

不能跳过的预检（生产清单骨架，直接抄）：

  1. 目标版本 release notes 全读，重点：API 废弃清单、默认值变化（如某探针默认值、seccomp 默认）、已知回归 issue。
  2. 废弃扫描：pluto/deprek8 扫 GitOps 仓库与 Helm chart 依赖。
  3. 组件兼容矩阵：CNI/CSI/存储/ingress/GPU operator 的版本支持矩阵逐个核对（CNI 落后是升级失败 Top1：kubelet 起来了但 CNI 不认新版本，节点 NotReady）。
  4. etcd 备份+验证（第 25 章）。
  5. 演练环境先走一遍完整流程（staging 同构）。
  6. 变更窗口+回滚预案（控制面升级 kubeadm 可回退的幅度有限，真正回滚手段是重建节点，预案要写清到哪一步之前可退）。

灾备的两个层次：

  • etcd 恢复：snapshot 恢复到新 etcd（etcdutl snapshot restore 初始化数据目录→逐个起成员）。适用于控制面数据损坏但节点/云资源还在。注意：恢复的 etcd 里包含旧的 cert/secret/IP 信息，跨环境恢复要做配置修正。
  • 集群重建：云资源没了（误删订阅/区域故障）。唯一可靠的路径是声明式重建：集群（IaC：terraform/集群厂商配置）+工作负载（GitOps 仓库 apply）+数据（PV 快照/对象存储恢复）+证书密钥（外部密钥系统）。每一段都有"自描述来源"才叫可重建；靠人脑记忆的配置=不可重建。RTO 的估算方法：拿这套流程在演练环境掐表。

多集群下的升级节奏：逐集群滚动（先非生产后生产），集群间版本差保持 ≤1 个次版本，避免 API 语义漂移伤到跨集群工具链。

27.3 实操 lab：kind 集群升级全流程彩排 + 灾备重建计时 ​

bash
# 1. 建一个落后版本的集群（用旧 node image，约 3 分钟）
cat <<'EOF' > /tmp/up.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: upgrade-lab
nodes: [{ role: control-plane }]
EOF
kind create cluster --name upgrade-lab --image kindest/node:v1.30.0 --config /tmp/up.yaml
kubectl --context kind-upgrade-lab version --short 2>/dev/null || kubectl --context kind-upgrade-lab version

# 2. 预检：废弃 API 扫描（装 pluto，约 30s）
brew install fairwinds/tap/pluto 2>/dev/null || (curl -sL https://github.com/FairwindsOps/pluto/releases/latest/download/pluto_5.21.2_darwin_arm64.tar.gz | tar xz -C /usr/local/bin pluto)
# 扫集群存量对象里的废弃 API：
pluto detect-all-in-cluster --context kind-upgrade-lab | head -15
# 扫 GitOps 仓库（对教程目录演示用法，生产指向你的清单仓库）：
# pluto detect-files -d ~/your-gitops-repo -r k8s

# 3. 制造一个"会炸的老资源"再扫（体验扫描器的价值）
kubectl --context kind-upgrade-lab apply -f - <<'EOF'
apiVersion: policy/v1beta1
kind: PodDisruptionBudget
metadata: { name: legacy-pdb, namespace: default }
spec:
  minAvailable: 1
  selector: { matchLabels: { app: none } }
EOF
pluto detect-all-in-cluster --context kind-upgrade-lab | head -8
# 预期：policy/v1beta1 被点名 deprecated/removed —— 这就是升级前要消灭的东西
kubectl --context kind-upgrade-lab delete pdb legacy-pdb

# 4. kind 的"升级"= 重建到新版本 + 恢复工作负载（这恰是灾备演练）
# 4a. 备份（用第 25 章手法，简化演示用 kubectl 导出应用层）
kubectl --context kind-upgrade-lab create deploy keepme --image=busybox:1.36 -- sleep 3600
mkdir -p /tmp/dr && kubectl --context kind-upgrade-lab get deploy,svc -A -o yaml > /tmp/dr/all.yaml

# 4b. "灾难"：删集群
kind delete cluster --name upgrade-lab

# 4c. 重建到 1.31（新版本）
kind create cluster --name upgrade-lab --image kindest/node:v1.31.0 --config /tmp/up.yaml
kubectl --context kind-upgrade-lab apply -f /tmp/dr/all.yaml
kubectl --context kind-upgrade-lab -n default get deploy keepme
# 预期：工作负载回来了。掐表：从 4b 到这里用了多久？这就是你应用层的最小 RTO 体感

# 5. 复盘两个数字写进你的运维文档模板：
#   - 集群冷启动时间：___分钟（IaC 化后=terraform apply 时间）
#   - 应用恢复时间：___分钟（GitOps 化后=argocd sync 时间，本 lab 的 all.yaml 就是它的手工形态）

预期总耗时 12-18 分钟（两次建集群占大头）。第 3 步扫描器点名废弃 API、第 4 步掐表，是两个带回生产的动作。

27.4 生产案例：公开复盘与事故模式 ​

案例一（公开可查证）：dockershim 移除（1.24）。K8s 官方提前多个版本宣布、迁移窗口一年以上，但大量团队仍在 1.24 升级日才发现节点容器运行时没换 containerd——节点起不来。这是"提前多年预警仍然踩坑"的行业标本。教训：升级检查清单里必须有"运行时/CNI/CSI 三件套版本核对"，且预警靠社区不如靠自己扫描。

案例二（公开可查证）：Google SRE 的经典事故复盘方法论（《SRE 书》的 postmortem 文化章节）被各公司 K8s 升级流程借用：升级也算"变更"，走变更管理（灰度、时限、回滚预案）。可引用的具体公开事实：GKE 的渐进式升级通道（rapid/regular/stable）本质上就是 Google 把内部灰度纪律产品化——你自管集群也应该有"先灰度一小撮节点池"的等价物。

案例三（行业通病，模式）："备份恢复不了"三部曲：备份只有一份且与集群同云同账号（区域故障时一起没）；恢复演练从没做过（第 25 章案例三）；PV 数据不在备份范围（只备了 etcd，忘了有状态服务的 PVC/快照策略）。灾难真正发生时的三连问：备份在哪、怎么恢复、数据呢？——每一问都答不上来就是本章的学费没交够，用 lab 第 4 步的掐表把三问变成三个数字。

27.5 本章面试题 ​

  1. 为什么 K8s 升级必须一次一个次版本？（API 兼容窗口按次版本设计，跳版本是未定义行为）
  2. 升级前检查清单前四条？（release notes/废弃扫描/组件兼容矩阵/etcd 备份验证）
  3. 节点升级和 PDB 什么关系？（drain 要尊重 PDB，无 PDB 的 drain=计划内停机）
  4. etcd 恢复与集群重建的适用场景区别？（控制面数据损坏 vs 云资源全失；后者的 RTO 由 IaC+GitOps+数据备份三段决定）
  5. 1.24 dockershim 事件给你什么流程启示？（预警再多也挡不住不做扫描的人；清单化+工具化）

27.6 自测清单 ​

  • [ ] 知道自己集群版本与官方支持窗口的差距
  • [ ] 会用 pluto 做废弃 API 扫描（集群+仓库两处）
  • [ ] lab 完成了"删集群→重建→恢复应用→掐表"全流程
  • [ ] 升级预检清单六条能默写
  • [ ] 有数据层备份策略（不只 etcd）

调研粮备注：lab 的 pluto 安装命令为参考（版本号请按 releases 页最新）；案例为公开事件与方法论，无内部升级事故复盘。

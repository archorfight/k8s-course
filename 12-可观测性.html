第 12 章 可观测性 — metrics / logs / tracing 三支柱落地 ​

心智图：

K8s原生只送你"三等座", 生产要自己升级: ​

​

metrics: kubectl top(秒级快照) ──→ Prometheus(时序库+PromQL+告警) ← 事实标准 ​

关键扩展指标: kube-state-metrics(对象状态) / node-exporter(节点) / 业务metrics ​

logs: kubectl logs(单Pod) ──→ stdout/stderr统一采集 ──→ Loki(索引标签不索引正文,便宜) ​

★黄金法则: 日志打stdout,别写文件; JSON结构化; 别多行栈轨迹裸奔 ​

tracing: K8s不管 ──→ OpenTelemetry SDK+Collector ──→ Jaeger/Tempo ​

跨Pod调用的"经络图", 排P99长尾的唯一利器 ​

​

告警哲学: 页面报警(Page)只留"用户可感/数据丢失风险", 其余进工单(Ticket) ​

``` ​

开篇判断 ​

  1. 我的 Pod CPU 用量查询（PromQL）能盲写吗？2) 告警列表里有多少条我收到也只会"哦"一声？3) 三支柱里哪根是 K8s 原生帮你搭好的？第二问超过一半，先做告警治理再看本章。

12.1 metrics：你要看的三层数据 ​

层 1 资源层（默认有）：metrics-server → kubectl top pod/node。排障够用，没有历史。

层 2 对象层（必装）：kube-state-metrics 把 etcd 里的对象状态变成指标：kube_deployment_status_replicas_unavailable、kube_pod_status_phase、kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}。"过去 24h 哪些 Pod 被 OOMKill 过"这种问题，没它你只能翻事件流。

层 3 应用层（你自己埋）：Spring Boot Actuator /actuator/prometheus（Micrometer）一行依赖；暴露 JVM 堆、GC 暂停、HikariCP 连接池、HTTP P99。这一层才是定位"K8s 说健康但用户说慢"的关键——因为 K8s 的探针只看进程，不看 P99。

Prometheus 生态的三个标准组件与部署形态（kube-prometheus-stack Helm chart 一把装齐）：Prometheus（拉模型，15s 抓取）+ Alertmanager（告警路由/静默/抑制）+ Grafana（看板，社区 dashboard 直接 import：15760 K8s 集群总览、13646 JVM 应用）。

PromQL 排障速记（拿着这五条能查 80% 问题）：

promql
# 每容器内存 vs limit 距离(找OOM边缘的)
sum by(pod)(container_memory_working_set_bytes{container!=""}) 
  / on(pod) kube_pod_container_resource_limits{resource="memory"}
# 滚动发布窗口内的5xx率
sum(rate(http_requests_total{code=~"5.."}[2m])) by (pod)
# CPU throttle率(第9章坑2的量化)
rate(container_cpu_cfs_throttled_periods_total[5m])
# HPA实际副本 vs 期望
kube_horizontalpodautoscaler_status_current_replicas
# 节点内存压力(驱逐前兆)
sum by(node)(node_memory_MemAvailable_bytes) / node_memory_MemTotal_bytes

12.2 logs：stdout 教条与它的例外 ​

K8s 的日志模型假设：容器把日志打到 stdout/stderr，kubelet 落到节点 /var/log/pods/，采集器（Fluent Bit/Loki Promtail/云厂商的 daemonset）统一收集，kubectl logs 立刻可读。工程守则：

  1. stdout 打结构化 JSON（一行一事件）：logback 的 LogstashEncoder，字段含 traceId/requestId。多行栈轨迹要由 logger 合并成单行（logback 的 %replace 或直接用异常的 JSON 序列化），否则采集器按行切割，一次异常变成 200 条垃圾。
  2. 不要写本地日志文件：文件日志轮转没人管、磁盘被吃满（节点 NotReady 的经典根因之一）、Pod 死了文件消失。老应用改不了文件日志？退一步：emptyDir + sidecar tail -f 转发 stdout。
  3. 保留期与成本：Loki 按标签索引、正文压缩（比 ES 便宜一个量级）；标签只放高基数可控的（namespace/app/pod），千万别放 userId 当标签（标签爆炸=索引爆炸）。
  4. PII 与合规：日志进集中系统后敏感字段要做脱敏（采集器 filter 或应用层），K8s 本身不提供这个。

kubectl logs 的四个高阶用法（第 15 章反复用）：--previous（上一次崩溃实例）、-l app=web --prefix --tail=50（按 label 聚合并标来源）、--since=10m、-f --all-containers。

12.3 tracing：K8s 不管，但你的分布式系统需要 ​

三支柱里 K8s 对 tracing 零原生支持，因为它是应用层协议。路径：OTel SDK（Java agent 一挂就有：java -javaagent:opentelemetry-javaagent.jar，Spring/Http客户端/JDBC 自动埋点）→ OTel Collector（daemonset 或 gateway）→ 后端（Jaeger 自建 / Tempo+Grafana / 云厂商 X-Ray）。trace 上下文跨 Pod 传播靠 W3C traceparent header，Service 的转发是 L4 透传不破坏它——但你自己代码里手搓 HTTP 客户端不带头，链路就断（和你过去在物理机上做全链路追踪一模一样，K8s 没加也没减难度）。

排障价值示例：用户报慢 → Grafana 看 trace waterfall → 发现 800ms 在 orders → db 的一段 span → span attributes 里有 Pod 名 → kubectl exec 进那个 Pod 看 GC 日志。三支柱在一条 trace 上闭环。

12.4 告警的最小充分集（SRE 入门） ​

照抄即可起步的页面告警（多一条都是疲劳轰炸）：

  1. SLO 燃尽率（错误预算消耗过快）——比"5xx>1%"高级一个段位。
  2. 容量红线：节点 requests 水位 >85%、PVC 使用 >90%。
  3. 可用性：Deployment unavailable replicas > 0 持续 5min；Pod 重启率突增（CrashLoop 探测）。
  4. 数据风险：etcd/PV 相关（托管集群则换云监控）。

其余全部降级为工单类（CI 里看、周会里看）。Alertmanager 的 inhibition（DB 挂了抑制下游应用的连环告警）配好，值班体验天壤之别。

Lab 12：装 Prometheus 栈 + Grafana 出第一张图 ​

bash
# 1. 装metrics-server(若Lab 11已装跳过) + kube-prometheus-stack (约3-5分钟)
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts 2>/dev/null || \
  (brew install helm && helm repo add prometheus-community https://prometheus-community.github.io/helm-charts)
helm repo update
kubectl create namespace monitoring
helm install kps prometheus-community/kube-prometheus-stack -n monitoring \
  --set grafana.adminPassword=admin --set prometheus.prometheusSpec.retention=2d

# 2. 等就绪
kubectl wait --for=condition=available deploy -l app.kubernetes.io/instance=kps -n monitoring --timeout=300s

# 3. 端口转发访问Grafana (浏览器开 localhost:3000, admin/admin)
kubectl port-forward -n monitoring svc/kps-grafana 3000:80 &
sleep 3 && echo "Grafana: http://localhost:3000 (admin/admin)"
# 验证动作: Dashboards → Import → 15760(K8s集群总览), 应已有数据

# 4. 用PromQL回答一个真实问题: 集群里哪个容器最接近OOM?
kubectl port-forward -n monitoring svc/kps-kube-prometheus-stack-prometheus 9090:9090 &
sleep 5    # ⚠️ port-forward就绪要几秒, sleep 2 不够, 太早curl会拿到空响应
curl -s 'http://localhost:9090/api/v1/query' --data-urlencode \
  'query=topk(5, sum by(pod)(container_memory_working_set_bytes{container!=""}) / on(pod) max by(pod)(kube_pod_container_resource_limits{resource="memory"}))' \
  | python3 -m json.tool | grep -E '"pod"|"value"' | head -10

# 5. 清理本lab的转发进程 (栈保留, 第14章还用)
kill %1 %2 2>/dev/null

验证点：Grafana 里能看到本 lab 集群的真实指标；PromQL topk 查询返回了最接近内存上限的容器（哪怕列表为空也证明链路通，返回的数组结构在 result.data）。

生产案例：可观测性反噬观测对象（行业高频模式） ​

监控栈自己成为故障源：每节点监控 agent 的 CPU 税（第 26 章定律 2）、Prometheus 全量 list 的 LIST 风暴（第 26 章定律 4）、保留期把磁盘打满——"观测者效应"在 K8s 里是实打实的容量问题。另一个方向的价值：本课程第 14 章全链路验证、第 24 章金丝雀门禁、第 21 章右配全部依赖本章的指标底座——可观测性是所有后续章节的前置。

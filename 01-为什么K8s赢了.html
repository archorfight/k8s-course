第 1 章 为什么 K8s 赢了 — 一次架构史复盘 ​

心智图：

  【问题演进】                【方案演进】                  【胜出原因】
  物理机部署太慢     ──→      虚拟化(vSphere)              资源利用率
       │                          │
  VM 仍然太重、       ──→      容器(Docker 2013)           秒级启动+镜像分发
  环境漂移没解决                │
  单机跑几百容器、   ──→      编排之争(2014-2017)          ★标准化API
  调度/发现/扩缩容              ├─ Swarm：把集群伪装成单机
  跨云/跨环境交付    ──→      ├─ Mesos：两层调度，强在批处理
                              └─ K8s：声明式API + 可扩展生态 ← 摘冠

开篇判断 ​

读本章前先自问：1) 我能说清"脚本部署"和"声明式部署"的一个本质区别吗？2) 我经历过一次凌晨手动救生产吗（它的哪个环节本可自动化）？3) 我理解"平台"和"工具"的差别吗？三问有一问卡壳，本章就是为你写的。

1.1 用你熟悉的方式理解：K8s 是"运行时的 Spring" ​

你写了十年 Java，这个类比会让你五分钟建立锚点（但注意它的边界，见 1.4）：

  • Spring IoC 容器管理 Bean 的生命周期：你声明 @Bean，容器负责创建、注入、销毁。
  • K8s 管理的是"集群中的一切"：你声明 Deployment，控制面负责创建 Pod、维持副本数、滚动替换。

两者共享同一个设计哲学：控制反转。你不调用 new Pod()，你提交一份期望状态的描述（YAML），由一个持续运行的调和循环（reconciliation loop）把现实拉向期望。这在 K8s 里有个正式名字：声明式 API + 控制器模式。理解这一点比记住任何一条 kubectl 命令都重要——因为 K8s 里所有对象（Deployment、Service、HPA、Job）全是同一个模式的不同实例。

1.2 编排之战复盘：为什么不是 Swarm 或 Mesos ​

作为架构判断，这场战争的结果值得复盘，因为同样的判断逻辑今天还在重演（比如 AI 推理框架之争）。

Swarm 的赌注：低门槛。 docker swarm init 一条命令起集群，把集群伪装成一台大 Docker 主机。它赌开发者要的是"更简单的 Docker"。输在：抽象太薄，稍微复杂的运维需求（金丝雀发布、细粒度网络策略、自定义调度）就得跳出它的模型自己造。对平台的采用曲线来说，"入门简单"的优势衰减极快，"天花板高"的优势随团队规模复利。

Mesos 的赌注：性能与两层调度。 诞生于 Twitter，强在大规模批处理与资源复用（同一集群跑 Spark + Web 服务）。输在：它把自己定位成"内核"（只做资源分配），要求上面再跑一个框架（Marathon、Aurora）来管应用——两层架构运维复杂、职责割裂，且核心团队精力被数据中心场景分走。通用性做得太底层，等于把复杂性转嫁给用户。

K8s 的赌注：API 即产品。 它的护城河不是调度算法多强（调度器早期甚至比较朴素），而是：

  1. 声明式 + 最终一致：API 对象是持久化的期望状态，任何组件（包括你写的 Operator）都能 watch 并作出反应。这让第三方扩展成为一等公民。
  2. CRD + Operator 生态：任何领域（数据库、消息队列、GPU、证书）都能用同一套 API 机制接入。生态飞轮：云厂商接 → 用户多 → 更多 Operator → 更难迁移。
  3. Google 的血统与 CNCF 中立化：Borg 十五年经验的设计投射 + 交给基金会避免了厂商锁定恐惧。2017 年三大云厂商（AWS/EKS 是 2018，但 GKE/AKS 已就位）全部支持后，战争实质结束。

一句话结论：Swarm 输给了天花板，Mesos 输给了产品化，K8s 赢在把"可扩展的 API 机制"本身当产品卖。你今天学 K8s，学的其实是一套事实标准的"分布式系统控制平面协议"。

1.3 它解决的真问题（对着你的分布式经验说） ​

把 K8s 的能力映射到你已经痛苦过的场景：

你过去的痛苦K8s 的对应机制对应章节
半夜机器挂了，服务得人工拉起控制器自动重建 Pod（自愈）3、4
发版=停机+祈祷Deployment 滚动发布 + readinessProbe4、10
服务发现靠配置文件+人肉同步Service + DNS（svc.ns.svc.cluster.local）5
流量突增，扩容靠打电话HPA 基于 CPU/内存/自定义指标伸缩11
配置散落各机器ConfigMap/Secret 统一分发7
测试环境和生产环境行为不一致同一份 YAML，声明式、版本化、可 GitOps全书

1.4 它不解决的问题（同样重要） ​

  • 不是 PaaS：它不帮你选语言、框架、数据库，也不替你写 CI/CD（那是 Argo CD / Flux 等上层的事）。
  • 不保证应用天然高可用：如果你的应用不处理 SIGTERM、不做健康检查、不幂等，K8s 反而会诚实地把这些问题放大到每次滚动发布时爆发（第 10 章整章讲这个）。
  • 有真实成本：控制面本身是要运维的复杂系统。小团队直接用托管版（GKE/EKS/AKS），别自建——除非你的规模大到托管费超过三个 SRE 的工资。

1.5 本章心智图回顾 ​

声明式 API（期望状态 YAML）
      + 控制器（watch → diff → act，永续调和）
      + 生态（CRD 让一切领域接入同一协议）
      = K8s = 分布式系统的事实标准控制平面

Lab 1：五分钟"体验一次调和循环" ​

目标：亲眼看到"删掉 Pod 它自动复活"——这是控制器模式的最低成本演示。

bash
# 1. 起一个最小集群（约 2-4 分钟，详见第 14 章完整安装）
brew install kind        # macOS；Linux 用 curl -LO https://kind.sigs.k8s.io/docs/user/quick-start/kind
kind create cluster --name k8s-lab --config /dev/stdin <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
EOF

# 2. 部署一个 Deployment（预期 10 秒内就绪）
kubectl create deployment demo --image=nginx:1.27 --replicas=2

# 3. 看控制器在干活
kubectl get pods -w        # -w 持续 watch，Ctrl+C 退出

# 4. 手动删一个 Pod（模拟故障）
kubectl delete pod -l app=demo

# 5. 回到第 3 步的 watch 窗口：新 Pod 立刻被创建
#    这就是调和循环：现实(1副本) ≠ 期望(2副本) → act

# 6. 收尾（本 lab 结束后集群保留，后面章节继续用）
kubectl delete deployment demo

验证点：删 Pod 后新 Pod 名字变了（demo-xxx-abcde → demo-xxx-vwxyz），说明是"重建"而不是"恢复"——Pod 是易碎品，Deployment 才是你对话的对象。

下一章我们把这张全景图拆开：控制面各组件到底在干什么，以及为什么"etcd 里的一条记录"是理解一切对象的起点。

生产案例：为什么 K8s 赢了（公开复盘） ​

编排之战的胜负手（公开可查证的复盘共识）：Swarm 输在"像 Docker 而不像平台"——它把集群当单机 API 的延伸，无法承载声明式调和与第三方扩展；Mesos 输在"两层调度"的定位——它要求你先在其上再建一层框架（Marathon 等），抽象不对齐最终用户的部署语义。K8s 赢的机制：开放 API + CRD 扩展模型，让整个生态（数据库、GPU、网络厂商）都在同一套声明式语义上生长。给你的选型启示：平台战争的胜负在扩展模型，不在功能清单——第 23 章 Operator 与第 16 章 Gateway API 都是这场胜利的延续。

本章面试题 ​

  1. K8s 和传统部署/虚拟机最本质的区别？（声明式调和循环 vs 命令式脚本）
  2. 为什么说 K8s 是"运行时的 Spring"？（IoC：你不调框架，框架调和你）
  3. Swarm/Mesos 为什么输？（扩展模型与抽象对齐，见案例）
  4. K8s 不解决什么？（业务容错语义、数据一致性、成本治理——都是你自己的工程）

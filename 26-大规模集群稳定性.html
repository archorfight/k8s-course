第 26 章 大规模集群稳定性 — 千节点之后的世界变了 ​

26.1 开篇判断 ​

集群规模每上一个数量级，K8s 的行为定性变化一次。自检：

  1. 节点数 >300？>1000？（>300 时你开始撞到"隐式上限"：每节点 110 Pod 的 allocatable、controller-manager 的调和队列长度、CoreDNS 的查询放大。）
  2. 有没有出现过"滚动发布一台台变慢、最后卡住"？那是 controller 同步队列的形状问题。
  3. 你知道集群的"变更日预算"吗？（大规模集群的核心稳定纪律是限速变更，不是修问题。）

本章的立场：大规模集群的稳定性 70% 来自"控制变更与余量"，30% 才是组件调优。

26.2 原理：规模化的五条物理定律 ​

定律 1 — 调和的 O(N) 放大。每个 Deployment 的 replicas×endpoint 变化都会触发 endpoint/controller 的重算与下发。10 万 Pod 集群里一次大发布=几十万次 watch 事件+endpoint 更新。1.27+ 的 EndpointSlice 与 SLO 改进缓解但不消除。工程含义：发布窗口错峰（不要周五下午全员 rollout restart），大集群用分批（rollout 的 surge 细粒度+暂停）。

定律 2 — 单节点上限与 DaemonSet 的宿命。每节点 110 Pod 上限（kubelet 默认，可调但神经要粗：每 Pod 一对 veth+cgroup，内核与 kubelet 都吃力）。DaemonSet 在 1000 节点=1000 份每节点的固定开销，日志 agent+监控 agent+mesh+安全 agent 各吃 0.1-0.5 核时，一台 8 核节点被"平台税"吃掉 1-2 核——第 21 章的成本账在这里再算一次。

定律 3 — DNS 是第一个倒下的。Pod 数×每秒请求×ndots 放大 = CoreDNS QPS。规模化标配：NodeLocal DNSCache（每节点缓存，消除主干上的 DNS 风暴）+ CoreDNS 横向扩容按 QPS 而不是副本数拍脑袋 + single-request-reopen（并发查询端口竞争问题，历史 Bug 的产物，至今仍是推荐配置）。

定律 4 — watch 与 LIST 的内存税。任何全量 LIST pod/service 的工具（自研脚本/监控 agent）在 10 万对象级会打出 apiserver 内存尖峰与 etcd 大读。规范：用 informer（共享缓存）或分页 list，禁用裸全量 list 进 cron 脚本——"crontab 里的 kubectl get pods -A" 是大集群的经典纵火犯。

定律 5 — 余量纪律。控制面 VM 规格与 etcd 磁盘要按目标规模的前 30% 配（ apiserver 内存粗算：每 1 万对象数百 MB 级，与 watch 客户端数强相关）；节点要有"驱逐余量"（system-reserved/kube-reserved 正确设置，第 9 章），否则节点压力级联驱逐会把一次流量高峰变成雪崩。

限流与降级三件套（规模化必配）：APF 分级（第 25 章）、Event 的 TTL 与聚合（events 占 etcd 写量的大头，--event-ttl 收紧）、controller-manager 的并发参数（如 --concurrent-deployment-syncs）按集群调，别用默认值扛十倍规模。

26.3 实操 lab：给 kind 集群做一次"规模压力剖面" ​

本 lab 不真造千节点，而是学会采集"规模敏感指标"——这些就是你到大规模集群里要盯的同一条曲线。

bash
# 1. 采集 API 对象规模剖面（你集群的"N"有多大）
kubectl get --raw /metrics | grep -E '^apiserver_storage_objects' | sort -t' ' -k2 -rn | head -8
# 看 resource 数量 Top：通常是 configmaps/secrets/endpointslices/pods
# 生产基线：pods>3万、endpointslices>5000 时要开始做第 26.2 的定律应对

# 2. 看 watch 客户端数（apiserver 内存的主要税源）
kubectl get --raw /metrics | grep -E 'apiserver_registered_watchers|watch_cache' | head -6

# 3. 看 LIST 的当前代价
kubectl get --raw /metrics | grep -E 'apiserver_request_list_total|etcd_request_duration_seconds_count.*LIST' | head -5
# 亲手制造一次 LIST 压力对比（小集群无感，但你要会看这个指标）：
time kubectl get pods -A > /dev/null

# 4. APF 现状：谁在排队/被拒
kubectl get --raw /metrics | grep -E 'apiserver_flowcontrol_(rejected|dispatched)_requests_total' | grep -v ' 0$' | head -10
kubectl get flowschema | head -10   # 默认分级一览

# 5. Event 写入占比（etcd 写量的大头）
kubectl get --raw /metrics | grep -E 'apiserver_storage_transformation|etcd_object_counts' | grep -i event | head -3

# 6. DaemonSet 平台税盘点（在大集群里这是必做审计）
kubectl get ds -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,WANTED:.status.desiredNumberScheduled,READY:.status.numberReady'
# 生产追问：每个 DS 的 CPU/内存 requests 是多少？加起来占节点百分之几？

# 7. 模拟发布风暴的微缩版：50 副本一次滚动
kubectl -n default create deployment storm --image=busybox:1.36 -- sleep 3600
kubectl -n default scale deploy storm --replicas=50
time kubectl -n default rollout status deploy/storm --timeout=120s
kubectl -n default delete deploy storm
# 生产对应物：1000 节点上这个时间的数量级是分钟级，且会牵动 endpoint/DNS/watch 全链路

预期总耗时 8-10 分钟。这个 lab 的产出是七条命令的"规模剖面采集脚本"，带到大集群直接可用。

26.4 生产案例：公开复盘与事故模式 ​

案例一（公开可查证）：K8s 官方与各大厂的规模化公开分享（如 KubeCon 的 scale 相关 talk、Kubernetes 特性 "LevelBasedTriggers"、以及 EndpointSlice 的动机文档）反复给出的同一组事实：kube-proxy 的 iptables 模式在 services×endpoints 数万级时规则更新要分钟级，这是 IPVS 模式与 eBPF dataplane 存在的直接原因。你的集群 services>1000 或 endpoints>1 万时，iptables 模式的更新延迟会在每次发布时放大——切 IPVS/eBPF 是规模化中期必答题。

案例二（行业通病，模式）：" Friday 大发布雪崩"。一次大规模滚动发布与流量高峰叠加，endpoint 更新延迟+就绪探针边界（第 10 章）导致可用容量瞬时下探，HPA（第 11 章）看到 CPU 升高再扩容，扩容又触发更多 endpoint 更新——正反馈。缓解：发布限速+错峰窗口+探针与 HPA 的参数联合评审（它们是一个系统不是三个组件）。

案例三（公开模式）：自研巡检脚本的 LIST 风暴。每分钟 kubectl get pods -A -o json 的 cron 脚本，在 5 万 Pod 的集群上每次拉几百 MB、打满 apiserver 内存与 etcd 读，恰逢业务高峰时 apiserver OOM。这个模式的公开变体极多（包括某些商业监控 agent 的旧版本）。规范落地：平台统一提供 informer 化的只读 API/工具，禁止裸 kubectl 全量进 cron——把第 26.2 定律 4 写进平台规范。

26.5 本章面试题 ​

  1. 大规模集群最先倒的三个组件？（CoreDNS/DNS 路径、kube-proxy(iptables 模式)、apiserver/etcd 的 LIST 与 watch 压力）
  2. iptables vs IPVS vs eBPF 的规模分界？（服务数千级时 iptables 更新分钟级；IPVS 哈希查找+增量；eBPF 内核映射）
  3. 为什么禁止 cron 里裸 kubectl get -A？（全量 LIST 的 apiserver/etcd 内存与带宽放大）
  4. APF 在大规模的价值？（分级保关键 API，防单点 client 引发的全局 429）
  5. DaemonSet 的规模化代价怎么审计？（节点固定开销×节点数的总量与占比）

26.6 自测清单 ​

  • [ ] 会采集对象规模/watch 数/LIST 代价三组指标
  • [ ] 能说出自己集群的 N（对象数/节点数）与对应档位的应对清单
  • [ ] 知道 kube-proxy 模式与切换成本
  • [ ] 有发布限速与错峰纪律（写进发布流程）
  • [ ] 会做 DaemonSet 平台税审计

调研粮备注：案例为 KubeCon/官方文档公开事实与行业模式；千节点级内部一手数据缺失，指标采集命令在小集群同样有效。

第 10 章 优雅终止 — 探针/信号/PDB/终止窗口（坑 4-7） ​

心智图：

一个Pod的一生里, 三个"死亡协议"决定服务不丢流量: ​

​

① 探针(健康三兄弟): ​

liveness 失败→重启容器 "你死了吗" (自愈) ​

readiness 失败→摘除流量 "你能接客吗" (发布/过载时主动摘) ​

startup 成功前屏蔽上两者 "JVM预热30s起步" (慢启动保护) ​

② 终止协议: SIGTERM → 等gracePeriod(默认30s) → SIGKILL ​

preStop钩子 + 应用graceful shutdown = 不丢进行中请求 ​

③ PDB: 中断预算(minAvailable/maxUnavailable), 滚动/驱逐/节点维护的并发闸 ​

​

乱序根源: "摘流量(endpoint)"与"发SIGTERM"并发执行, 谁先谁后无保证 ​

→ preStop sleep 5-10s 就是买时间的老土但100%有效的解法 ​

坑 4：livenessProbe 配成慢接口 → 自愈变自杀；坑 5：没有 graceful shutdown → 滚动发布 502；坑 6：PDB 缺失或过紧 → 发布卡死/维护时全灭；坑 7：terminationGracePeriodSeconds 太短 → 大请求被腰斩。

开篇判断 ​

  1. SIGTERM 到 SIGKILL 之间发生了什么？2) preStop 存在的意义我说得清吗？3) 我的每个线上服务都有 PDB 吗？第三问答不上来，你们下一次节点操作就是一次计划内停机。

10.1 探针设计（坑 4） ​

yaml
readinessProbe:                    # 先说结论: 每个对外服务必配
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 3              # 连续3次失败才摘 → 容忍瞬时抖动
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
startupProbe:                      # 慢启动应用(JVM/Spring/模型加载)必配
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 60             # 最多等5min, 期间liveness不生效

四条资深守则：

  1. liveness 和 readiness 必须是不同的语义。liveness 只回答"进程是否死锁/不可恢复"，绝不查下游依赖（DB 连不上 → liveness 失败 → 重启 → 雪崩：重启不解决 DB 问题，但重启风暴放大了故障）。依赖健康放 readiness：DB 挂 → 摘流量 → 上游熔断，不重启。Spring Boot 用 health groups 把两者分开是标准做法。
  2. liveness 接口必须轻。配了一个要查 DB 的 /health、超时 1s、阈值 3 次——DB 慢一点，全实例连环重启。这不是假设，是无数事故报告的第一条。
  3. 慢启动用 startupProbe，别靠 initialDelaySeconds 猜。模型加载 3 分钟的应用，initialDelay 调成 200s 意味着快速崩溃也要等 200s 才能重启探测；startupProbe 做到了"等多久都行，好了立刻接管"。
  4. TCP 探针只证明端口开着，不代表能处理请求；exec 探针开销大且排障难。默认 httpGet。

10.2 终止协议全时序（坑 5、7 的解剖图） ​

kubectl delete pod / 滚动替换 /驱逐，全部走同一条协议：

T+0    Pod进入Terminating
       ├─ (并行A) endpoint控制器把它从Service/EndpointSlice摘除 → 现有连接继续, 新流量不来
       ├─ (并行B) kubelet执行preStop钩子(若配置)
T+x    preStop结束 → kubelet发SIGTERM(PID 1)
       ├─ 应用应: 停止accept → 处理完存量请求(带deadline) → 退出(exit 0/143)
       └─ 应用没处理SIGTERM? PID 1的坑见下
T+30s  (默认gracePeriod) 还没退 → SIGKILL → 137

三个坑的对症药：

  • 坑 5（滚动 502）：应用立刻退出 + 摘流量晚到。药方双管齐下：① 应用 graceful shutdown（Spring Boot 2.3+ 原生 server.shutdown: graceful；Go http.Server.Shutdown(ctx)；"等存量请求清空"有 20s 上限）；② preStop sleep 补偿摘流量的传播延迟（endpoint 摘除 → 各节点 kube-proxy/conntrack 更新需要 1-2 秒）：
yaml
    lifecycle:
      preStop:
        exec: { command: ["sh","-c","sleep 5"] }
    terminationGracePeriodSeconds: 45        # 覆盖 preStop 5s + 处理期40s
  • 坑 7（gracePeriod 太短）：大文件上传/批量任务/长推理请求被 30s 默认值腰斩。推理服务（单请求 30-120s）必须把 gracePeriod 拉到 P99 请求时长 + 10s，同时优雅退出时"拒绝新请求但等存量完成"。
  • PID 1 陷阱：容器里 JVM 是 PID 1 能收到 SIGTERM；但 sh -c "java -jar app.jar" 的话 sh 不转发信号，你的 graceful shutdown 永远不触发，30s 后一律 137。解法：ENTRYPOINT 直exec、或 exec java -jar、或加 init: true（shareProcessNamespace 不必要）。验证方式：kubectl exec pod -- kill -TERM 1 后看应用日志是否打印 shutdown hook——这个 5 分钟的检查能避免一类"怎么配置都 502"的玄学。

10.3 PDB：中断预算（坑 6） ​

yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web }
spec:
  minAvailable: 2        # 或 maxUnavailable: 1。同一PDB只能有一个
  selector: { matchLabels: { app: web } }

PDB 只约束自愿中断（Voluntary Disruption）：节点排水（drain）、 autoscaler 缩节点、Karpenter 整机型替换。滚动发布不经过 PDB（那是 Deployment 的 maxUnavailable 管的）——两个机制分管两条路，这点很多文章讲错。

  • 没有 PDB：节点维护时 5 副本可能同时被 drain → 服务裸奔甚至全灭。对多副本服务，PDB 是上生产的准入项。
  • PDB 过紧（replicas=2 且 minAvailable=2）：任何 drain 永久阻塞 → 节点池操作卡死、cluster-autoscaler 缩容失败、运维半夜骂街。replicas=2 配 minAvailable=1 或 maxUnavailable=1；replicas=1 的服务别设 PDB（设了=永不允许中断，自相矛盾），改为接受短暂中断。
  • 排查"drain 卡住"：kubectl get pdb 看 ALLOWED DISRUPTIONS（0 = 被挡）。

10.4 面向 AI 推理服务的特殊终止设计（承上启下） ​

第 13 章的 GPU 应用把本章所有机制用到极致：推理请求耗时长（gracePeriod 大）、模型加载慢（startupProbe 长）、单副本贵（PDB 紧 + maxUnavailable=0）。在这里先埋一句话：优雅终止设计 = 排队论问题：终止窗口 ≥ 排队中的请求 × 处理时间的期望，而不是拍脑袋 30 秒。

Lab 10：实证"无优雅终止会 502，加了就没事" ​

bash
# 场景: 一个"收SIGTERM立刻退出"的服务 vs "等存量完成"的服务

# 1. 部署无优雅终止版 (busybox收到TERM即死) + Service
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: { name: naive }
spec:
  replicas: 3
  selector: { matchLabels: { app: naive } }
  template:
    metadata: { labels: { app: naive } }
    spec:
      terminationGracePeriodSeconds: 1
      containers:
      - name: app
        image: hashicorp/http-echo:1.0
        args: ["-text=naive","-listen=:80"]
        readinessProbe: { httpGet: { path: /, port: 80 } }
---
apiVersion: v1
kind: Service
metadata: { name: naive }
spec: { selector: { app: naive }, ports: [ { port: 80 } ] }
EOF
kubectl rollout status deploy/naive

# 2. 起一个持续打流的客户端(每50ms一次, 记录失败)
kubectl run loader --image=curlimages/curl:8.8.0 --restart=Never -- \
  sh -c 'ok=0; fail=0; while true; do curl -s --max-time 2 http://naive >/dev/null && ok=$((ok+1)) || fail=$((fail+1)); echo "ok=$ok fail=$fail"; sleep 0.05; done' 
kubectl wait --for=condition=ready pod/loader --timeout=60s 2>/dev/null

# 3. 滚动重启, 同时观察客户端失败计数上涨
kubectl rollout restart deploy/naive
sleep 25
kubectl logs loader | tail -3          # fail 明显增长 = 滚动丢请求实锤

# 4. 改造成优雅版: preStop sleep + 长gracePeriod
kubectl patch deploy naive -p '{"spec":{"template":{"spec":{"terminationGracePeriodSeconds":30,"containers":[{"name":"app","lifecycle":{"preStop":{"exec":{"command":["sleep","7"]}}}}]}}}}'
kubectl wait --for=condition=available deploy/naive --timeout=120s
POD=$(kubectl get pod -l run=loader -o jsonpath='{.items[0].metadata.name}'); kubectl exec $POD -- sh -c 'true' 2>/dev/null
kubectl rollout restart deploy/naive
sleep 40
kubectl logs loader | tail -3          # fail 增长显著放缓(说明摘流量与终止的时序被preStop抹平)

# 5. 清理
kubectl delete pod loader --force --grace-period=0; kubectl delete deploy,svc naive

验证点：两次滚动之间失败计数增速的差异就是 preStop + gracePeriod 的价值。⚠️ http-echo 本身不处理 SIGTERM，剩余失败来自"连接被关"而非"请求被拒"——真实效果取决于你的应用 graceful shutdown 质量，这正是本 lab 想让你带走的判断标准：拿失败计数当 A/B 指标，验证你的服务终止配置，而不是信任何模板。

生产案例：Spot 回收与节点 drain 的三重奏（行业高频模式） ​

Spot 被回收（2 分钟告警）+ 无 PDB + 无优雅终止 = 批量回收时服务雪崩——第 21 章成本治理的前提条件。同构事故：节点升级 drain 把无 PDB 服务打成不可用（第 27 章）。本课程 lab 实测数据：无优雅版滚动 fail 显著增长，preStop+grace30 版增长放缓——这两个数字就是给管理层讲"优雅终止值多少钱"的证据。

本章面试题 ​

  1. 终止协议全时序（摘端点→preStop→SIGTERM→宽限期→SIGKILL）？
  2. PDB 管什么不管什么？（voluntary disruption 管，Pod 自身崩溃不管）
  3. preStop 和容器内信号处理怎么分工？
  4. terminationGracePeriodSeconds 默认值？给 AI 推理服务怎么定？（按最长在途请求+排空时间，原文 10.4）

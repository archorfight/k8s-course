第 11 章 弹性伸缩 — HPA 抖动/VPA 重建/节点伸缩（坑 8-10） ​

心智图：

三层伸缩, 各管一段, 谁也不替代谁: ​

​

HPA (横向: Pod数) ← 指标驱动(CPU/内存/自定义QPS) ​

VPA (纵向: Pod规格) ← 历史用量推荐requests (in-place模式有限GA, 默认仍重建Pod) ​

Cluster Autoscaler/Karpenter (节点数) ← Pod调度不上才加节点(被动) ​

​

完整链路: 流量→HPA加Pod→Pending→节点 autoscaler 加Node→Pod上车 (分钟级!) ​

★ 伸缩不是瞬时的: 你的扩容延迟 = 指标采样15-30s + Pod启动 + 可能的节点拉起2-5min ​

所以"靠HPA接住秒级流量脉冲"是幻想, 预扩容+限流兜底才是正解 ​

坑 8：HPA 与 VPA 同时管一个指标打架 + HPA 抖动（throttling 循环）；坑 9：requests 设错让 HPA 读数失真；坑 10：把节点伸缩当即时资源，忽略冷启动。

开篇判断 ​

  1. HPA 的目标值是绝对值还是利用率？它和 requests 什么关系？2) 我的 HPA 抖过吗、怎么止住的？3) 节点扩容的分钟级延迟我的扩缩容策略考虑了吗？第一问答不出，你的 HPA 参数大概率是抄来的。

11.1 HPA 工作原理：一个控制回路 ​

HPA控制器 每15s(默认--horizontal-pod-autoscaler-sync-period):
  目标副本 = ceil( 当前副本 × max(当前指标/目标指标) )
  例: 3副本, CPU当前80%, 目标50% → 3×80/50 = 4.8 → 5副本
  变化方向限制: 扩容无限制(每周期最多×2 pod数, 默认), 缩容要"冷静期"(默认5min)

前提依赖（都是坑 9 的化身）：

  • metrics-server 必须装（kind/裸集群默认没有！kubectl top pod 一样依赖它）。
  • HPA 的 CPU 百分比 = usage/requests。requests 虚高 → 永远达不到阈值 → 永不扩容；requests 虚低 → 一启动就 100%+ → 疯狂扩容。调 HPA 之前先校准 requests，这是新人排 HPA "不工作"的第一站。
  • readiness 未通过的 Pod 不计入指标（防"没就绪的副本拉低均值"假象——但反过来 Pod 启动期 CPU 高会拉高均值，见坑 8 的抖动）。
yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: web }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: web }
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
  behavior:                            # ★v2的行为控制 = 抖动的解药
    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容冷静5min, 防锯齿
      policies: [ { type: Percent, value: 25, periodSeconds: 60 } ]  # 每60s最多减25%
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - { type: Percent, value: 100, periodSeconds: 60 }   # 激进扩
      - { type: Pods, value: 4, periodSeconds: 60 }
      selectPolicy: Max

11.2 坑 8 详解：三种抖动形态与药方 ​

形态 A：throttle 循环。CPU limit 设了 1 核 → 流量来 → usage 顶到 limit → HPA 看到 100% → 扩容 → 流量摊薄。看着正常？问题在 limit 造成的 throttle 本身制造了延迟，HPA 把"被自己掐死"误读为"需要扩容"。药方：给 HPA 管的服务不设 CPU limit（第 9 章派 A），或 limit 远高于 requests。

形态 B：启动脉冲。新 Pod 启动（JVM 预热、缓存冷）CPU 冲高 → 拉高平均 → 再扩 → 过会儿全部回落 → 缩。锯齿。药方：自定义指标（QPS/队列长度）替代 CPU；或 startupProbe 期间接受指标失真并设置 scaleUp 上限 + scaleDown 冷静期 10min。

形态 C：HPA 与 VPA 打架。VPA 看到 requests 偏高 → 建议调低 → requests 下降 → HPA 的 utilization 分母变小 → 读数升高 → 扩容。官方也承认二者在 CPU 上互斥。药方：VPA 用 recommendation 模式（只推荐不执行），或 VPA 只管内存不管 CPU（mode: Auto + 只设 memory 的 target）。

自定义指标才是终态：CPU 是代理指标，业务真值是 QPS/P95/队列深度。keda（基于 Prometheus/Kafka/云队列事件驱动伸缩，还支持缩到 0）是事实标准工具——批处理消费者按队列积压扩缩，比 CPU 精确一个量级。KEDA 的 scale-to-zero 对"夜间无流量的内部服务"省钱效果显著。

11.3 坑 9：requests 与 HPA 的耦合（校准清单） ​

□ kubectl top pod -l app=web 采样至少覆盖早高峰/午间/晚高峰
□ requests.cpu ≈ 常态P50×1.2 (让日常utilization落在30-50%)
□ HPA target 60-70% (留出burst余量)
□ 若Pod启动CPU是稳态的5倍+ → 换自定义指标或加stabilization
□ maxReplicas×requests ≤ namespace ResourceQuota (否则扩到一半被quota卡死)
□ maxReplicas×requests ≤ 节点池可承载量 (否则扩出的Pod在Pending等节点, 见坑10)

11.4 坑 10：节点伸缩的物理延迟 ​

Cluster Autoscaler（云厂商托管版）与新一代 Karpenter 的共同逻辑：只有"因资源不足 Pending 超过一定时间"的 Pod 才触发加节点（CA 默认 10s 评估 + 启动机器 1-5min + 镜像拉取）。即节点层扩容是分钟级的被动响应。三个工程结论：

  1. 洪峰可预期的服务（大促、定时批任务）用预扩容：kubectl scale --replicas=N 或 HPA 的定时预热（KEDA cron scaler），别赌 autoscaler 反应速度。
  2. 节点冷启动可优化：Karpenter 按 Pod 的真实 requests 挑机型（不绑节点组）+ 优先 spot（抢占式实例）；镜像预热（预热 daemonset 拉镜像/镜像加速）。AI 推理的大镜像（10GB+）让节点冷启动翻倍，第 13 章专门讲解法。
  3. 缩节点比加节点更危险：drain 要过 PDB（第 10 章），缩容策略配 scaleDown.unneededTime（默认 10min）和 utilization threshold。spot 被回收 = 非自愿中断，靠 PDB+多拓扑分布+graceful termination 组合拳兜住。

11.5 给 Java 服务的完整弹性模板（可抄） ​

requests.cpu = P50×1.2, 不设cpu limit
requests.memory = limits.memory = 峰值×1.2
HPA: min 3 (跨AZ拓扑分布), max 20, target 60%, 缩容冷静600s
KEDA或自定义QPS指标替代CPU(可选但推荐)
PDB: maxUnavailable 1
VPA: recommendation模式, 每月看一次报告手调requests
节点: Karpenter/托管CA + 预期洪峰前手动预扩

Lab 11：让 HPA 真的转起来（含抖动观察） ​

bash
# 1. 装metrics-server (kind默认没有, HPA的地基)
# (⚠️ 原链接 .../v0.7.2/manifest/base.yaml 已404; 且新manifest把args整体替换会崩——
#  容器根文件系统只读, 自签证书目录建不出来, 必须补 --cert-dir=/tmp)
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl patch deployment metrics-server -n kube-system -p \
  '{"spec":{"template":{"spec":{"containers":[{"name":"metrics-server","args":["--kubelet-insecure-tls","--cert-dir=/tmp","--secure-port=10250"]}]}}}}'
kubectl wait --for=condition=available deploy/metrics-server -n kube-system --timeout=120s
kubectl top nodes    # 能出数=地基OK

# 2. 部署带requests的目标 + HPA
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: { name: hpa-demo }
spec:
  replicas: 1
  selector: { matchLabels: { app: hpa-demo } }
  template:
    metadata: { labels: { app: hpa-demo } }
    spec:
      containers:
      - name: app
        image: polinux/stress:1.0.4
        resources: { requests: { cpu: 100m } }
        command: ["stress"]
EOF
kubectl set resources deploy/hpa-demo --limits=cpu=300m  # 仅为了本lab可制造压力(生产按第9章!)
cat <<'EOF' | kubectl apply -f -
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: hpa-demo }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: hpa-demo }
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 50 } }
  behavior:
    scaleDown: { stabilizationWindowSeconds: 60 }
EOF

# 3. 加压: 把容器的stress命令换成烧CPU
kubectl patch deploy hpa-demo -p '{"spec":{"template":{"spec":{"containers":[{"name":"app","command":["stress","--cpu","2","--timeout","600s"]}]}}}}'

# 4. 观察 (另开终端: watch -n5 kubectl get hpa,pods -l app=hpa-demo)
kubectl get hpa hpa-demo -w
# 预期: 15-30s内 TARGETS 从 <unknown>/50% 变为 200%+/50% → REPLICAS 1→2→4→5(上限)

# 5. 停压观察缩容冷静期
kubectl patch deploy hpa-demo -p '{"spec":{"template":{"spec":{"containers":[{"name":"app","command":["sleep","600"]}]}}}}'
# 等待1-2min: utilization跌回0%, 但REPLICAS保持60s冷静期后才逐级缩

# 6. 清理 (⚠️ 原写法 kubectl delete hpa,hpa-demo --all 语法非法)
kubectl delete hpa --all; kubectl delete deploy hpa-demo

验证点：①无 metrics-server 时 HPA 的 &lt;unknown&gt; 症状见过（排障条件反射）；②扩容 15-30 秒、缩容被冷静期拖住——两个时间常数记进直觉。

生产案例：HPA 与发布/Spot 的正反馈（行业高频模式） ​

发布时可用容量瞬时下探→CPU 升高→HPA 扩容→endpoint 变更又触发更多传播开销——高峰期发布+HPA 组合的正反馈雪崩（第 26 章定律 2 的展开）。另一模式：metrics-server 版本坑（本课程实测 v0.7.2 旧 manifest 404、新 manifest 需 --cert-dir=/tmp，VERIFICATION.md 第 11 章记录）——HPA"没反应"先查指标链路。
